# Mamal-Trading — Maturity & Status (single source of truth for "how finished is it")

This document is the **only** binding statement about maturity. If any other document suggests something else ("done", "ready"), **this** one wins.

## Status vocabulary (5 levels, ascending)
| Level | Meaning | Reached by |
|---|---|---|
| 1 · **built** | code exists | implementation |
| 2 · **compiles** | F7 = 0 errors in MetaEditor | F7 run by the user |
| 3 · **fix-verified (AI)** | adversarial AI review (multi-agent workflow) with no confirmed finding | verify workflows — **no live test!** |
| 4 · **live-tested** | executed on demo, behaviour observed (rule test matrix + demo forward) | user on a demo account |
| 5 · **verified / ready** | full rule matrix green + demo forward stable + prop-firm compliance per firm | everything above + firm-specific sign-off |

> **"fix-verified (0 problems)" ≠ "tested".** It means exactly one thing: an AI review workflow did not confirm a bug. Real testing is level 4.

## Current overall status (EA v0.61 · cockpit server v0.62)
**Level 2 (compiles) for the ENTIRE state: F7 on EA v0.62 = 0 errors / 0 warnings — the compile proof has been carried along with every batch since v0.45. The cockpit server sits at v0.62 (Node/browser, not compiled — there is no F7 equivalent for it, only live operation). v0.18–v0.62 are therefore at level 2–3 (adversarial AI verify rounds were run for every batch, recognisable by the `(Verify)` fixes in the code) · level 4/5 NOT reached — not a single live test.**

> **v0.62 (EA)** = **THE WEEKLY OBLIGATION NEVER TOOK EFFECT — and the first fix was worse than the bug.** Found while reviewing the documentation, not in a test: `WeekRiskSet()` requires `RG_WEEK_RISK_IDX` = the current week — but the weekly roll **set that index itself**. That meant every new week was automatically "confirmed": the required weekly decision happened **exactly once**, at the very first start. Every Monday after that the panel silently showed "AKTIV" (active). A test case would not have caught this — it simulated the week change via F3 and would have been green.
>
> **First fix attempt: refuted 3:0 adversarially.** The obvious solution (let the confirmation expire on the roll) left `RG_EFF_RISK` at the input default. Consequence: **R1 would have force-liquidated every weekend position on Monday** that had been correctly sized against the confirmed weekly value — the losing close would have counted as trader fault in the loss streak and cooldown, and at the same time the gate would have blocked reopening. Two more holes: the "obligation yes/no" decision hung on the inputs of **the master instance** (a chart with the chooser switched off would have lifted the gate for **everyone**), and because the weekly block only runs once a week, a brief config change on Sunday would have silently disabled the obligation **for the whole week**.
>
> **Second round: refuted 4:0 again.** The same force-close damage came back through the **pre-booking path**: the roll unconditionally activated a pre-booked **reduction**, and `EnforceRisk` ran in the **same cycle**. Mirror image: a pre-booked **increase** would have loosened the entire auto-scale cascade in a week that was never confirmed — exactly what the obligation is built against.
>
> **Final state.** `RG_WEEK_RISK_IDX` is now set **only by `SetWeekRisk()`**, i.e. exclusively through a real confirmation. The **value** still carries over (`RG_WEEK_RISK`/`RG_EFF_RISK`) so that R1/R2/R12 do not force-close anything. A **pre-booking** survives the roll unconsumed and on Monday only pre-fills the input field. A single source `WeekRiskPending()` feeds the gate, the panel status, the greying-out of the button, the field border and the sub-line — deliberately from the **local** inputs of each instance. On top of that, the **cockpit JSON did not know R23 at all**: the dashboard showed a green "AKTIV" (active) while the panel was locking — now `weekRiskPending` exists as its own flag with a blue status level. In the process it turned out that `blockReason()` in the dashboard emitted **hard-coded German** despite the `block.*` keys being present; the banner is now wired up (DE/EN/FA).
>
> **Lesson (object lesson 2).** A confirmation must not be renewed by the same place that advances the period — otherwise the system confirms itself. And: whoever introduces a gate has to check what the **value** behind that gate triggers elsewhere; here half the enforcement cascade depended on it.

> **v0.62 (cockpit)** = **TRADE FILE — every single trade becomes traceable.** From all journal lines belonging to **one ticket** the server builds a file: `/trades` (list, the last 200 tickets, newest first), `/trade?ticket=…` (the file), `/shot/<file>` (image), page `trade.html`. Access via the **📁** button in the dashboard header; every journal line with a ticket is clickable.
>
> **What the file contains.** Metrics per trade: **planned risk** = `Risk%` × `Balance` **of the OPEN line** (journal columns 14 and 4) — i.e. the risk that applied at the moment of entry, not one calculated after the fact; number of SL/TP moves, of which risk-increasing and risk-reducing; candle third of the entry; realised net. Plus an **automatically worded plain-text summary**, the screenshots in **chronological order** (entry, moves, exit) with full-screen zoom, and the chronicle of the moves with the respective verdict. For **closed** trades there is additionally the plan ↔ result comparison: if the loss exceeds the planned risk by more than **15 %**, the file names the factor and the possible causes ("Der Verlust liegt 3,6× über dem geplanten Risiko — Ursache prüfen: verschobener Stop, Slippage oder Gap" — the loss is 3.6× the planned risk; check the cause: moved stop, slippage or gap); if it stays below, that is explicitly confirmed as "genau so soll ein Stop wirken" (this is exactly how a stop is supposed to work). This is the first place in the tool where **plan and outcome of the same trade stand side by side**.
>
> **Path hardening.** `/shot/` accepts only names that exactly match the EA pattern (`^Mamal_\d+_[a-z0-9]+_\d+\.png$`) — a `../` escape cannot even be expressed; reading happens only inside the folder of the requested account.
>
> **Hidden coupling — belongs commented at both ends.** The scoring of the trade file reads the **German verdict texts of the EA** out of the journal tag via regex ("Risiko ERHOEHT" — risk increased, "Risiko gesenkt" — risk reduced, "Gewinn abgekuerzt" — profit cut short, "Ziel vergroessert" — target enlarged). That journal entries stay German is, since v0.62, **no longer a matter of style but a precondition**: translating the journal tags would silently zero out the statistics of the trade file — with no error message, and with the page still populated.

> **v0.53–v0.61** = **MULTILINGUALITY — and the most expensive search-and-replace run of this project.** Dashboard **DE/EN/FA** via `i18n.js` (**346 keys per language**, switcher in the header); Persian with **RTL layout** (`html[dir="rtl"]`), where numbers, amounts and times stay left-to-right (`direction:ltr` + `unicode-bidi:embed` on the number classes) — otherwise the sign slid to the wrong side, and after the colour analysis it is precisely the sign that carries the message. Panel **DE/EN** via `InpLang`: `T(key)` and `TF(key,{0}…{3})` with placeholders **instead of `%s`/`%d`**, so that the order of the values stays free per language (in English it is often different); an unknown key returns the key itself and is immediately visible in the panel instead of leaving a blank. Journal entries deliberately stay German (audit trail — and since v0.62 technically necessary too, see above).
>
> **v0.61 INFINITE RECURSION (object lesson 1).** The automated run that replaced the German panel texts with `T("…")` also ran **over the translation table itself**: in **22 entries** the return value then contained another `T()` call on the same key — `T()` called itself until the stack was full. Symptom: the EA died **in the middle of drawing the panel**, the panel stayed half-drawn, and the log showed a stack overflow. Anyone looking only at the panel would have assumed a drawing bug; in reality the instance was dead — and with it, if it was the master instance, all of enforcement.
>
> **Lesson:** a replacement run must **never** touch the translation table — it is the sink, not the source. It needs an excluded region and afterwards a counter-check for "no `T(`/`TF(` inside `T()`".
>
> **Leftovers from the same run, still in the code:** **13 dead keys** `misc.artifact*` in which code fragments (`",Symbol(),dir,lot,…`) ended up as "text". They are harmless — both language branches return the same thing, and there is **not a single call site** — but they show the blast radius of the run. And they inflate the table: of the **153 entries, 13 are junk, the real number is 140**. Cleaning that up is cosmetics; reading the key count as a measure of progress is not.

> **v0.52** = **Candle thirds — the question "am I entering early or chasing?" becomes measurable.** The EA appends a machine-readable **`K1/3`…`K3/3`** to every `OPEN` line (elapsed time × 3 / `PeriodSeconds()`). From this the cockpit computes the **net per third** and shows "Einstieg in der Kerze: früh/mittig/spät" (entry within the candle: early/middle/late) — the evaluation you never give yourself honestly. In addition (`InpCandleTimeOnChart`) the countdown is also drawn as an `OBJ_TEXT` **right next to the running candle** (anchored one slot to the right of `Time[0]` at the level of the bid, moving along with it), coloured green/orange/red according to the elapsed third — the same logic that is also logged.

> **v0.49–v0.51** = **WEEKLY RISK BECOMES MANDATORY — an operation turns into a rule.** Instead of `[-]`/`[+]` there is a real input field (`OBJ_EDIT`) plus a **SETZEN** (set) button; Enter in the field (`CHARTEVENT_OBJECT_ENDEDIT`) confirms just the same. **A decimal comma is accepted** (MQL4 would otherwise read "0,25" as **0** and silently discard the input), `%` and spaces are stripped; outside 0 < v ≤ 1.0 % the value is rejected and the field is reset to the valid state.
>
> **The real finding is in the drawing.** `DrawPanel` runs **2×/s**. If it rewrote the field text every time, it would wipe out the user's input under their fingers. The text is therefore **written only when the valid value changes**. v0.50 additionally clears away the objects of the old `[-]`/`[+]` variant — otherwise they sat as ghosts over the field and the number appeared twice.
>
> **`InpRequireWeeklyRisk` (default on): without a defined weekly risk there is NO trading.** Panel status **"RISIKO FESTLEGEN"** (define risk), BUY/SELL greyed out, field border highlighted in blue. Every new week the definition expires (week index) → **a fresh deliberate decision**. The **first** choice of the week takes effect immediately (it also sets `RG_EFF_RISK`, otherwise the daily tighten-only layer would push it straight back down); **every later change only takes effect from Monday — including a reduction.** Deliberately chosen risk is bound for the week, no fiddling around while on tilt.
>
> **Honest limits.** (1) This is a **new hard entry gate**: a mis-operation (field left empty, week change overnight) blocks trading completely — exactly as intended, but it belongs in the matrix as its own test case. (2) The gate hangs **on `InpRiskChooser`**: whoever switches off the chooser switches off the obligation with it. (3) The definition lives **exclusively in GlobalVariables** (`RG_WEEK_RISK`, `RG_WEEK_RISK_IDX`) — **not** in the signed lockstate file. Deleting them via F3 does lock things at first (fail-closed), but afterwards the next entry becomes a free **first choice of the week** again: the binding is therefore the same impulse brake as in v0.30, not a real lock.

> **v0.47** = **SCREENSHOTS + BEHAVIOUR TRACKING — the raw material for the trade file.** One image per action with the ticket in the name: `Mamal_<ticket>_<open|close|slmove|tpmove>_<epoch>.png` (`ChartScreenShot`, `InpShotWidth`=1100 / `InpShotHeight`=620). Cleanup happens according to `InpShotKeepDays` (14) in the 60-second housekeeping, **capped at 200 deletions per pass** — a folder filling up must not block the cycle with I/O.
>
> **`TrackSLTP()`** remembers the last seen SL/TP per ticket (`RGSLS_`/`RGTPS_`) and judges every change **in substance rather than merely logging it**: SL further away = "Risiko ERHOEHT (nachteilhaft)" (risk increased, adverse), SL closer = "Risiko gesenkt (vorteilhaft)" (risk reduced, favourable) (with break-even detection), SL removed = "Risiko unbegrenzt" (risk unlimited), TP closer = "Gewinn abgekürzt" (profit cut short), TP further = "Ziel vergrößert" (target enlarged). Journal event **`SLTP_MOVE`**, plus a screenshot.
>
> **The finding:** during an ongoing **user modify series** nothing is **counted** (gate: no modify quiet, no occupied trade context, ≥2 s apart). Otherwise **every intermediate step of the drag** would count as its own move, and a single hand movement would appear in the statistics as a dozen risk increases. What is scored is the **result after letting go** — the same quiet window that has prevented the Wine crash since v0.31 carries the data quality here.
>
> **Honest limits.** One image per action is real file I/O in the EA thread; `InpScreenshots=false` switches both off, and without images the trade file stays a pure text file. Only what is `InScope()` **or** registered as a panel ticket is captured — foreign EA magics do not show up in the tracking.

> **v0.48** = **two fixes, one of them relevant to the numbers.** **Panel:** a **manually** set `InpPanelScale` may now also **shrink** (clamp 0.5–3.0). Previously a lower bound of 1.0 cut off every wish for a smaller panel; the **AUTO** derivation from the screen DPI deliberately stays at ≥1.0 so that small DPI values do not shrink anything.
>
> **Multi-account (the more important part).** Several accounts in the **same terminal** share **one** journal file. Without an account specification the server summed up **all** accounts — the numbers of the old account stuck to the new one (net, calendar, blocks). Three parts: (1) the dashboard picks **the live running account whenever no explicit choice was made** (from `state.account`); (2) accounts that only exist in the journal appear in the switcher as **"nur Historie"** (history only) — previously there was no entry for them at all; (3) an old account finds its journal via **its own lines** (`;<account>;`), no longer via the `cockpit.json` in the folder, which after a login change has long belonged to the new account. This is not a display detail: an account's hit rate, calendar and loss streak depended on it.

> **v0.46** = **RISK FREE, TP line, lock monitor — and the first `OrderModify` of the project.** The button **"RISK FREE"** (`InpBreakEvenBtn`, default on) pulls the SL of **all positions in profit** to break-even. Break-even is **exactly `OrderOpenPrice()`**: MT4 opens a BUY at the ask and closes at the bid (and vice versa) — so the spread is **already inside the entry price**; `InpBreakEvenBufferPts` additionally covers the commission. The button **never loosens an SL** (if it is already at or beyond the target: skipped), checks `MODE_STOPLEVEL` (too close to the market → skipped instead of error 130) and runs **even during a lock and a cooldown** — pure risk reduction is never blocked, the only gate is `IsTradeContextBusy()`. Reach: only what the tool is responsible for (`InScope()` **or** a registered panel ticket); **foreign magics are deliberately left untouched**, because their EA logic may depend on their own SL. Every move lands in the journal as **`BREAKEVEN`**, failures with an error code.
>
> **This belongs in the test matrix, not in the feature list.** Up to v0.45 the sentence specifically verified in v0.31 held: "the EA has **only three** trade operations — `OrderClose`/`OrderDelete` in the protected queue and `OrderSend` in the user click, **no `OrderModify`**". That is exactly what stopped being true in v0.46. The cause of the Wine crash was **two trade operations on one ticket**; the new path checks the trade context **once on entering the function** — not, as the close queue has done since v0.31, **immediately before every single operation** — and the loop runs with `RefreshRates()` across all positions. It is always triggered by a user click and not by the timer, but the case "user drags the SL on chart A while RISK FREE runs over all positions" is constructible. **Provoke it deliberately on demo.**
>
> **Draggable TP line** (`InpTpLine`, default off): takes precedence over the auto TP from `InpRR` — **but only if it lies on the correct side of the entry**; otherwise the auto TP stays. R8 (minimum R:R) then checks unchanged. **Panel header:** live spread in points, amber from 1.4× and red from 2× the broker's normal spread (`MODE_SPREAD`), plus the remaining time of the running candle (green → amber from 30 s → red from 10 s). **Presentation:** `InpFontScale` (type) and `InpShapeScale` (tiles/buttons) scale separately (0.5–2.0 each); `InpPanelAutoFit` shrinks the panel if it would be taller than the chart window (lower bound 0.6) — against cut-off buttons on small and split charts.
>
> **Cockpit lock monitor.** A prominent countdown (mm:ss or h:mm:ss) that keeps running in the browser **between** server polls (1-second tick, re-sync on every `/state`). It covers cooldown, day lock, week lock, max loss and "Tagesziel erreicht" (daily target reached); the max-loss lock honestly shows **"bis manuell aufgehoben"** (until lifted manually) instead of a clock that does not exist. **Honest limit:** the clock computes client-side towards the next server midnight — the EA remains authoritative.
>
> **Redesign + colour logic (validated).** Institutional blue-black colour world. Green/red is **not distinguishable** for colour-blind users (measured ΔE 4.1) — therefore **the number with its sign always** carries the message, never the colour alone; area encodings (hour stripes) use a single-hue, validated blue sequence, the calendar is number-first with a thin accent stroke. Contrast checked above WCAG AA in both themes.

> **Two object lessons, one pattern.** The **infinite recursion (v0.61)** and the **master deadlock (v0.42)** are the same class of bug: **silent total failure with the user interface still running.** In the deadlock the panel carried on normally while enforcement, close scoring and cockpit writes had stopped; in the recursion a half-drawn panel stayed on screen while the instance was already dead. In both cases "looks normal" was no proof of "is running", and in both cases the finding came not from an error message but from an observation by the user. **Consequence for testing: every test question must hang on an effect, not on a display** — was the journal line written? does the lock really bite? is the `BootDiag` line there? The 30-second `PROTECT_OFF` alarm from v0.42 is exactly the right shape for this and should be the model for further watchdogs.

> **Maturity after v0.46–v0.62: unchanged level 2–3.** F7 on v0.61 = 0 errors / 0 warnings is level 2 for the entire state — **and nothing more**. What has been added is code that **writes into open positions** (`OrderModify` in RISK FREE), a **new hard entry gate** (`InpRequireWeeklyRisk`), **file I/O in the EA thread** (one screenshot per action) and a **text layer over everything** (translation) whose failure mode has already produced a total outage once. The cockpit part (trade file, multilinguality, multi-account) is **display without rule influence** — with the caveat that the trade file depends on the German journal texts. **Level 4 is not one step closer: there still is not a single live test.**

> **v0.44/v0.45** = **manual trades become visible — without bending the rules.** Every trade that did not go through the panel (by hand in the order window, from a phone, foreign EA magics) is written by the master as its own journal event **`CLOSE_MAN`** (`ResolveManualHistory`) and marked in the cockpit as **"manuell"** (manual): orange line in the journal (`bd-man`), **✋** in the calendar day, its own statistics tile "Davon manuell" (of which manual), column "davon manuell" (of which manual) in the weekly report.
>
> **Scoring — deliberately asymmetric.** Manual trades count **towards the net** (calendar, hit rate, profit factor, expectancy — it is real money) but influence **NO rule**: no loss streak (R6), no cooldown (R5), no R3 daily budget. The scope design of enforcement therefore stays untouched; the dashboard merely tells the truth about the account balance. **Discipline side:** a day with manual trades **breaks the streak** and colours the trend bar orange (`clean(d)` = no block **and** nothing done past the panel) — previously the streak "days without a rule block" kept running while the trader traded around the tool all day long.
>
> **The real finding is in the dedup (v0.43, critical).** The `RGP_` markers (processed positions) used to be **pruned immediately with the close floor** — only the very last one survived. For `ResolveHistory` that had no consequence (there the floor itself protects), but the **ticket fallback from v0.40 checks exactly those markers**: it found none and scored **everything a second time** — duplicate `CLOSE` lines, **duplicate loss streak**, duplicate net in the calendar. Fix: **6 h grace period** for `RGP_`. Plus a **shared `RGM_` marker** that *both* paths set, so that the same trade never runs into the net as `CLOSE` **and** as `CLOSE_MAN` (scope/magic change); cross-check against the rule path (`IsProcessedAny` incl. legacy key) and `HasOpenRemainder` (a partial close is only reported once the position is fully closed). Aggregation window **7 days backwards**, reporting window **today's server day** — otherwise a partial close that began yesterday reports only a fraction of the net.
>
> **Cockpit server v0.45:** journal **parse cache** (invalidated via mtime+size) instead of a full parse of the daily growing CSV on every 1.5-second poll (noticeable on a OneDrive/AV-scanned path); `/journal` **filters first and truncates afterwards** — previously `slice(-80)` cut into the raw data, so that periodic `INFO` lines pushed real events out of the list.
>
> **Honest limits.** R22 is on by default and closes manual orders (magic 0) anyway — in practice `CLOSE_MAN` mostly captures **foreign EA magics**, phone trades **between two enforcement cycles** and everything R22 does not catch (EA/AutoTrading off, no master). Only what is inside the **loaded account history range** is visible (documented `OrdersHistoryTotal` weakness). If creating the GV marker fails (name length/GV limit), `INFO` is journalled **once** and after that **nothing at all** is displayed — deliberately, better no display than a journal flood every second. And fundamentally: this is **display, not protection**.

> **v0.42** = **MASTER DEADLOCK — the most critical finding of this project.** Since v0.28 **only the master instance** does enforcement, close scoring and cockpit writes. The release in `OnDeinit` **deleted** `RG_MASTER` — and `GlobalVariableSetOnCondition` **cannot create a missing** variable (err 4058). Result: after removing a master chart (or deleting the GV via F3) **a master election was NEVER possible again**. Enforcement (R4/R4b/R6/R22 …), close scoring (loss streak, daily budget) and cockpit updates **stood still** — and did so **invisibly**: the panel kept running, BUY/SELL stayed clickable on every chart, the lock display showed the last state. That is the explanation for how the protection could fail **without a single error in the log**.
>
> **Fix (three parts).** (1) Release via **`Set(RG_MASTER, 0)`** instead of `Del` — the slot continues to exist, the next instance takes it over atomically right away. (2) The election creates a **missing** slot via `GlobalVariableTemp` *before* `SetOnCondition` claims it; the atomicity of the claim is preserved (exactly **one** wins). (3) **Alarm after 30 s without a master** — notify + `PROTECT_OFF` in the journal. Sharpened afterwards: **v0.43** only raises the alarm when **really nobody** is master (a passive instance is the normal case and must not warn constantly); **v0.45** makes the alarm **time-based instead of cycle-based** (the cycle rate depends on `InpTimerSeconds`) and also defuses the latch when transitioning **into** the master state.
>
> **Diagnosis instead of guessing.** Every instance writes a `BootDiag` line into the journal at start: number of registered tickets (`RGOPN`), `OrdersHistoryTotal`, close floor, trade context, `InpMagic` and whether the master slot exists at all. Without that line the state was indistinguishable from "running normally" from the outside.
>
> **Consequence for maturity.** This is **not a feature** but a previously unnoticed **total failure of the protection** under a completely everyday operation (closing a chart). It belongs in the matrix as **test case no. 1**: remove the master chart → a second instance must take over within seconds; delete `RG_MASTER` via F3 → the election must work again; terminal restart; and the 30-second alarm must actually fire when no instance is running any more.

> **v0.40** = **Close buttons + ticket-based close detection.** Four panel buttons: **FULL CLOSE / CHART CLOSE / FULL 50% / CHART 50%**. Reach is **account-wide incl. foreign magics** (a deliberate user decision), "CHART" = only the symbol of this chart; **50%** halves every position rounding **down** to the lot step, with a min-lot guard for **both the half AND the remainder** and an FP epsilon (in binary `0.06*0.5` otherwise became `0.02` instead of `0.03`); **pending orders stay untouched**. No confirmation dialog — and the buttons run **even during a lock/cooldown**: **risk reduction is never blocked**. The only gate is `IsTradeContextBusy`. The target tickets are **frozen before the first close**, because the pool mutates during the closes (the 50 % remainder gets a new ticket) and MQL4 guarantees no pool ordering.
>
> **No `MarkEaClosed`** — deliberately: for panel trades the losses realised this way count **normally** towards the loss streak and cooldown (trader decision, not a laundering window). Trades of **foreign** magics are only journalled (`PANEL_CLOSE`), their P/L stays outside the scoring by scope design.
>
> **Ticket registry `RGOPN_<ticket>`.** Every ticket opened by the panel is registered; `ResolveByTicketRegistry` resolves closes via `SELECT_BY_TICKET` — **independently of the magic number and of the period filter of the account history tab**, with **group aggregation across all legs** of the same position (previously the fallback only scored the first leg iterated and swallowed the P/L of the siblings: winning leg first → streak reset despite a net loss). The remainder ticket of a 50 % close is registered afterwards, preferably via the MT4 standard comment "from #<ticket>", with the fallback only on an **exact** match of time/price/magic/remaining lots.
>
> **`InpMagic<=0` is hard-corrected to 990201 in `OnInit`** (panel trades need a unique identifier; with magic 0 they would be indistinguishable from manual trades and R22 would have cleared out **its own** trades). The older failsafe "R22 disables itself at magic 0" stands beside it as a second safeguard. Also: the cockpit button now reports honestly when `InpCockpit=false` instead of leaving the user puzzling over "Daten veraltet" (data stale).

> **v0.39** = **Dashboard expansion + the first writing channel back into the EA.** Pure display, **no rule influence** — with one exception, see "Tag beenden" (end day).
>
> **New in the cockpit:** **buffer gauge** (three tiles from `dayBase`/`initBal`/`weekBase`: "Heute noch verlierbar" — still losable today, "Bis Max-Verlust" — until max loss, "Diese Woche noch verlierbar" — still losable this week — in account currency instead of percent, with a traffic light); **challenge tracker** (target 10 % / 5 % / freely selectable, progress against `initBal`, **trading day counter** incl. a note about the FTMO minimum of 4, projection from the daily average); **tilt radar** (**≥4 rejections in 10 minutes** → pulsing red bar with a prompt to take a break); **cooldown countdown** as an R5 card (mm:ss + bar); **browser notifications + sound** on state changes (cooldown over — but only when really **nothing** is blocking any more —, day/max/week lock, daily target); **discipline trend** (30 active days) **+ streak** "Tage ohne Regel-Block" (days without a rule block) with a record; **trade statistics** (hit rate, avg. win, avg. loss, profit factor, expectancy, best/weakest hour); **equity curve** — the **server** samples the equity of every live-writing account every 5 s into `cockpit/data/equity_<account>.csv` (the **EA stays unchanged**; the file is trimmed hourly to ~20 k points), and the curve draws in the **daily loss limit** as a dashed line; **dark mode**; **multi-account grid** with remaining buffer per card; **printable weekly report** (`/report.html`).
>
> **"Tag beenden" (end day) — voluntary self-lock, strictly tighten-only.** Button in the dashboard → `POST /cmd/endday?acct=…` → the server writes `mamal_cmd.txt` into the files folder **of exactly that account** → the EA (only as master) reads it, **deletes** it and sets `RG_LOCK_UNTIL` via **`MathMax`** to the next server midnight: an already **longer** lock is never shortened, **loosening is fundamentally impossible through this channel**, and the result is persisted immediately. **Server side:** POST only, **origin check** (a cross-site form POST would carry `Host: localhost` and would otherwise get through), **`acct` mandatory** (with two live-writing terminals the lock would otherwise have landed in the **wrong** account), the account parameter reduced to digits; the server still binds only to **127.0.0.1** and checks the Host header against DNS rebinding. **EA side:** a command file that cannot be deleted (read-only/AV lock) is reported **once** and ignored afterwards, instead of being executed again on every cycle.
>
> **Honest classification.** This is the **first writing connection from the browser into the EA**. It is deliberately limited to **a single, exclusively tightening** command — the worst abuse would be an *additional* lock. **Any extension of this channel is security-relevant** and must not happen casually.

> **v0.38** = **ZERO CONFIG — the account base now comes from the broker, not from an input.** `DepositBase()` derives the challenge base from the **first deposit** (history type 6, profit > 0); an implausibly small "deposit" (**< 10 % of the balance**, e.g. a fee refund with a filtered history tab) is discarded — it would effectively have disabled R4b, because the drawdown clamps to 0 against a far too small base. The fallback is the current balance (with a note to set the account history tab to "Gesamte Historie" — entire history). The **daily base** is reconstructed from the history via `ReconstructedBalanceAt(ServerDayStart())`. Every source counts as **confirmed immediately** and is persisted (GlobalVariable **and** lockstate file) — **"BASIS UNSICHER" (base uncertain) is thereby practically abolished**, and the associated fail-closed block from v0.34 goes away. `InpInitialBalance`/`InpDayStartBase` are now only an **optional override**; **tighten-only stays active in the auto branch too** (an already confirmed higher base is never lowered by a lower derivation, lowering via input only takes effect at the day change).
>
> **Fail-closed remains exactly one case:** `g_initialBalance <= 0`, i.e. **no broker handshake** (typical in the autostart race: the EA loads before balance/history are there) → no new trades. The master cycle **heals this itself** as soon as `AccountBalance() > 0`, and reports the base once loaded.
>
> **Multi-account.** The EA writes one signpost **`mamal_files_<login>.txt`** per login into the common folder (in addition to the legacy `mamal_files.txt`); from these the server builds the **account switcher** (`?acct=…`) and the grid. Safeguarded: a **stale signpost** after a login change is caught (the `cockpit.json` in the target folder must carry the same account), `/state` **never** delivers data of a foreign account under the requested label, journal lines of foreign accounts are filtered via the account column, and the legacy signpost no longer has **priority** (with two live-writing terminals the display otherwise jumped between accounts). The master **publishes its `InpMagic`** (`RG_MAGIC`); a passive chart with a deviating magic warns **once, clearly** — its panel trades would be invisible to the master and therefore **unguarded**.
>
> **Autostart.** `MamalCockpit.vbs` in the Windows autostart launches the cockpit server without a window, waits for the OneDrive mount and runs with **`MAMAL_QUIETSTART=1`** — **no** browser popup at boot, while the cockpit click in the EA still opens it. Matching this, **ancient trigger files** (a click while the server was dead) are now only **cleaned up**, not opened any more. *The `.vbs` lives in the user's autostart folder, not in the repo.*

> **v0.35** = **a new rule: R22 "Panel trades only"** (`InpCloseManualTrades`, default **on**). Every order with magic number **0** — i.e. every trade opened by hand in the MT4 window — is detected and **closed after the fact**: positions at bid/ask with `InpSlippage`, pending orders via `OrderDelete`, reason `"R22 Manueller Trade — nur Panel-Trades erlaubt"` (R22 manual trade — only panel trades allowed) or `"R22 Manuelle Pending-Order — nur Panel-Trades erlaubt"` (R22 manual pending order — only panel trades allowed). **Why at all:** the panel path (`DoEntry`) is the only one that passes through the entry gates — AutoTrading, lock, uncertain base, R4b warn gate, R13 daily target, R5 cooldown, R16 session/news, R25 revenge, R14 minimum pause, R7 SL line/side, R15 broker `STOPLEVEL` + min SL, R1 lot calculation, R2 idea cap, R3 daily budget, R12 heat, R17 correlation. A trade placed by hand bypasses **all** of them; until now, under `WatchScope=TOOL_ONLY` (default, enforced in FundedMode), it was not even closed during an active lock but at most nagged about once per minute.
>
> **Three deliberate decisions — each with its price:**
> - **Delimitation solely via `Magic != 0`.** Anything with a foreign magic stays untouched, so R22 does not interfere with other EAs — for that no symbol or scope check is needed, and R22 acts **account-wide across all symbols**, not just on the EA's chart symbol. **Price:** the distinction "mine/not mine" hangs on this single number. `InpMagic` defaults to `990201` and panel trades are sent with it — whoever sets `InpMagic=0` lets R22 clear out **its own** panel trades. There is **no protection in the code** against this.
> - **No grandfathering at start.** Open hand trades that are already on the account when the EA is attached are not exempt. `OnInit` counts and reports them (notify + journal, event `INFO`, tag "R22 Start: N manuelle Order(s) vorgefunden -> werden geschlossen" — R22 start: N manual order(s) found -> will be closed), but closes **nothing** itself — the actual close happens in the first cycle in which the instance is a **confirmed master** (≥2 cycles), and on a passive instance not at all. So whoever drops the EA onto an account with running hand positions loses them — just not in the same second.
> - **Applies in FundedMode too.** R22 does **not** hang on `InScope()` and is therefore the **only** enforcement function that bypasses the scope safety design; FundedMode does force `WatchScope` hard to `TOOL_ONLY`, but R22 closes anyway. Consequence: **in FundedMode the EA closes positions it did not open itself.** This is compliance-relevant and **must be verified per prop firm** — the startup warning about `ALL_POSITIONS` does not cover this case, because R22 acts independently of the scope.
>
> **Honest limits.** R22 is **detect-and-revert**, not prevention: the trade goes through, is filled and is then reversed at market price — **the trader bears spread and slippage**. The detection latency follows from the code, not from a measurement: timer 1 s or tick ≥500 ms, plus close throttle 300 ms (`InpCloseThrottleMs`), plus possibly up to 2 s modify quiet (hard-capped at a 10 s series — so whoever keeps dragging the SL delays R22), plus retry/backoff on errors; realistically **fractions of a second up to several seconds**, with the market closed (error 132) up to **15 min per attempt**. If the EA is not running, **AutoTrading is off** or `EventSetTimer` fails, R22 does **not** take effect at all — like all of enforcement. After `InpCloseRetries`=5 failed attempts the ticket leaves the queue with FINAL-FAIL and **stays open**; it is re-queued on the next pass. The re-validation of the close reason (`CloseReasonStillValid`) applies **only to positions** — a queued pending is deleted even if `InpCloseManualTrades` had meanwhile been set to `false`.
>
> **Interaction with the loss rules (important).** A hand trade closed by R22 is out of scope under `TOOL_ONLY`/FundedMode: it does **not** count for R5 cooldown, R6 loss streak, R19 de-risk, R25 revenge and consumes **no** R3 daily budget. The realised loss does however very much hit the **equity-based** limits — **R4 daily loss, R4b max loss, R18 weekly limit**. R22 does not count as trader fault in the sense of the loss streak scoring (only R7/R1/R8 do).
>
> **Cockpit.** With `InpCloseManualTrades=false` R22 appears in the dashboard as a "— aus" (— off) chip. In "Deine Schwächen" (your weaknesses) R22 only appears via the fallback of the cockpit server (the EA's RuleId column stays empty because the close tags start with "Queue"). **Honest limit of the statistics:** every journal line with `CLOSE` and a RuleId is counted — every retry, every FINAL-FAIL and every discard produces its own — so **a single hand trade can appear several times in the R22 counter**. The `INFO` entry from `OnInit`, by contrast, does not distort anything (INFO is not scored). **R22 does not appear in the on-chart panel at all.**
>

A new rule is not a maturity gain, quite the opposite: R22 is **new, untested code that intervenes sharply in open positions** — it sends `OrderClose`/`OrderDelete` at orders the EA never opened itself, account-wide and without a scope filter. Exactly the path on which the Wine crash cause hung in v0.31. > **v0.34** = **Audit-driven hardening wave — the largest batch of this project.** A **multi-agent code audit** produced **69 confirmed findings**; severities **high** and **medium** are dealt with (low deliberately left open). No new feature, no changed rule *values* — throughout, hardening of existing rules against circumvention, restart, account change and mis-operation.
>
> **Base & time.** `InpDayStartBase` now only takes effect on the **first start** — previously the input reset the midnight base on *every* subsequent day and could thereby shift the R4 calculation permanently. An **automatically guessed** account base is now **fail-closed** (no new trades) until `InpInitialBalance` = the real challenge starting balance has been confirmed; this is the case "tool is installed AFTER a loss", in which the R4b lock would otherwise have sat *below* the prop firm limit. New is an **account binding** (`RG_ACCOUNT`): if the login changes, the entire stored state is discarded instead of carrying foreign locks/anchors forward. A **late daily/weekly roll** (terminal was off) reconstructs the anchor balance from the **broker history** at the real rollover moment instead of taking "now". The **server offset** is persisted (`RG_SRV_OFFSET`) and no longer seeded from a stale `TimeCurrent` when the EA starts in a tickless phase. The **R4b base additionally lives in the lockstate file** (field 9, signed) and therefore survives the **4-week expiry** of the GlobalVariables.
>
> **No-override (R10).** The lockstate is now reconciled **periodically every 5 s**, not only at start: whoever deletes the `RG_*` GlobalVariables gets still **active** locks back from the **signed file**, and the deletion lands in the journal as **`TAMPER`** (expired locks are deliberately not revived). The TestMode **"reset" is no longer a universal unlock**: it only works on a **demo account** and only for locks **set by the test button itself** (`RG_TEST_SET`); real rule locks and the **R4b hard lock always stay**, and a rejected reset is logged as `TAMPER`. `InpDayResetHour`/`InpWeekStartDay` only take effect at the **real rollover** (`RG_EFF_RH`/`RG_EFF_WS`) — you can no longer "roll away" a running lock by adjusting the hour. **Base inputs and all lock-relevant inputs are tighten-only** (lowering the base intraday is rejected and journalled), and **`InpTightenOnly` itself is latched** (`RG_TIGHT_LATCH`) — the self-lock was previously switchable off with a single input flip, which made it worthless as a self-lock.
>
> **Enforcement.** Protective closes by the EA with **trader fault** (R7 SL/TP removed, R1 over-risk, R8 R:R) now count **towards the loss streak** (`RGEACF_<ticket>`) — previously you could have a running loss closed by the EA by deliberately removing the SL, and it did **not** count for R5/R6 ("loss laundering"). Genuine protective flats (R12, lock `SafeCloseAll`) still deliberately do not count. The **entry rules R5/R13/R16/R25 are enforced after the fact** (`EnforceEntryState`): pendings that run into a lock window are deleted, and positions opened during a lock are closed — previously these rules only applied at the moment of the click. New is an **R2 monitor** (`EnforceIdea`) that watches the idea cap after the entry as well. In addition: the **modify quiet window** (the v0.31 Wine fix) is **hard-capped** (max. 10 s series), so that constantly shoving the SL cannot mute enforcement arbitrarily long; the **close queue re-validates the reason** immediately before closing (`CloseReasonStillValid`), so it no longer closes anything because of a cause that has since resolved; the **partial-close deferral** is time-limited (a 0.01-lot remainder could otherwise postpone the loss scoring indefinitely); the **R7 grace is persistent + has a healing period** (`RG_NK_`/`RG_NKH_`, see `RULES.md` R7); and a **history visibility watchdog** (`HistoryVisibilityWatch`) raises a loud alarm when a **filtered account history tab** makes closed trades invisible — otherwise loss streak and daily budget would simply not have counted.
>
> **Robustness / audit trail.** The **journal CSV** opens with `FILE_SHARE_READ|FILE_SHARE_WRITE` + a short retry and screams on failure instead of **silently** losing lines (an audit trail with gaps is not one). The **lockstate is fail-closed on a read error too** instead of fail-open. **Naked positions** (without SL) are conservatively evaluated in the **entry gates** with the full risk per trade instead of **0 %** — previously a position without an SL arithmetically opened room for further trades.
>
> **Cockpit** (pure display, no rule logic): the **R4b warn gate now appears in the banner** — previously the dashboard showed a green "Alles frei" (all clear) while the EA blocked every new trade; real **offline/stale display** instead of frozen values; the **rule statistics no longer lose lock/cooldown blocks** (the EA fills the RuleId column only when the tag starts with "Rxx"; the server now derives it conservatively).
>
> **Maturity: unchanged.** This remains **fix-verified (AI review) but LIVE-UNTESTED** — level 3. Hardening is not maturity: not a single one of these 69 findings was reproduced live. **F7 is still outstanding**, as is the **tier 1 test matrix** (`TEST-MATRIX-TIER1.md`). And because this is the **largest batch so far** — many new GlobalVariables and **four new enforcement functions** (`EnforceIdea`, `EnforceEntryState`, `HistoryVisibilityWatch`, `PruneNaked`), all of which reach into the hot cycle path — it is also the **riskiest**: it has to be tested especially thoroughly, including regressions in rules that worked before. A batch of this size without a live test is **not** progress towards level 4.

## What the next level requires
- **→ Level 2 (compiles): DONE.** F7 on **v0.61** = 0 errors / 0 warnings; the compile proof has been carried along with every batch since v0.45. The cockpit server (v0.62) is not compiled — there is no F7 equivalent for it, only live operation. **From here on the live test is the only thing still missing**, and there is no excuse left for postponing it.
- **→ Level 4 (live-tested):** rule test matrix green on demo (trigger every rule in practice mode + manually, incl. restart/partial close/same-second/close fail/lockstate corrupt) **and** a demo forward test stable over several days/symbols. **New mandatory test cases from v0.38–v0.62:**
  - **Master handoff (priority 1):** remove the master chart → does another instance take over within seconds? delete `RG_MASTER` via F3 → is an election possible again? With **no** instance running any more: does the 30-second alarm (`PROTECT_OFF`) come?
  - **Auto base:** account with a complete and with a **filtered** history; account with several deposits; start **before** the broker handshake (self-healing); counter-check that the derived base really is the challenge base that R4b computes against.
  - **Close buttons:** full and 50 % on positions at the min-lot boundary, with a foreign magic, **during an active lock**, and the scoring of the remainder ticket in the loss streak.
  - **Dedup:** the same trade must land in the streak, the daily budget and the calendar **exactly once** after a restart, a partial close and a magic change (`RGP_`/`RGM_`/ticket fallback against each other).
  - **Command channel:** "Tag beenden" (end day) with two running terminals (does the lock land in the right account?), a second click (no shortening), a `mamal_cmd.txt` that cannot be deleted.
  - **RISK FREE (priority 1 after the master handoff):** SL to break-even with several open positions **while** an SL is being dragged by hand on another chart (the v0.31 crash path — now with `OrderModify`); a position barely in profit (the `MODE_STOPLEVEL` case); a position with an already tighter SL (must **not** be loosened); execution **during an active lock/cooldown**; a position with a foreign magic (must stay untouched).
  - **Weekly risk obligation:** a fresh week without a definition → are BUY/SELL really blocked? is "0,25" accepted with a comma? typing while the panel is drawing (the field text must not be overwritten); a change within the week only takes effect on Monday — **including a reduction**; delete `RG_WEEK_RISK` via F3 → locked at first, afterwards a free first choice again (a documented limit, not a bug).
  - **Screenshots:** let the folder fill up beyond `InpShotKeepDays` (does the 200 cap clear it cleanly without blocking the cycle?); `InpScreenshots=false` (does the trade file stay textually complete?); behaviour with a locked/full file system.
  - **Behaviour tracking:** drag an SL in **one** movement over several intermediate steps → **exactly one** `SLTP_MOVE` line must result, not one per intermediate step.
  - **Multi-account:** two logins one after another in the same terminal → does the dashboard show the **live** running account without an account choice, does the old account find its history, and is the calendar free of foreign numbers?
  - **Language:** have the panel drawn **completely** with `InpLang=LANG_EN` (the recursion from v0.61 surfaced exactly here — half-drawn panel = dead instance) and check the dashboard in `fa` with RTL: signs, amounts and times must stay left-to-right.
- **→ Level 5 (ready):** additionally prop-firm rule compliance clarified per target firm (+ possibly a Windows VPS for real no-override). What remains open is the firm-specific assessment that the EA **closes foreign positions it did not open itself** (R22 and the close buttons).
